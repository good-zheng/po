做一个带 AI 的功能，演示时最容易，上线最难。演示环境里所有依赖都是通的；生产里它们会分别在你没准备的时候坏掉。所以设计阶段就先决定：坏掉时用户看到什么。

## 四层退路

烹饪助手对外只有一条 WebSocket 通道，里面串了四个可能坏的外部依赖，每个都有自己的降级：

| 依赖不可用                       | 退到哪一层                     | 用户感知                       |
| -------------------------------- | ------------------------------ | ------------------------------ |
| 语言模型（限流、鉴权失效、超时） | 回显式模型，返回固定结构的应答 | 回答变笨，但有回应             |
| Redis（会话存储）                | 内存检查点                     | 单轮正常，跨轮记不住上下文     |
| 向量嵌入服务                     | 关键词路由                     | 意图判断变粗糙，不会全落兜底   |
| 整条网络                         | 本地规则引擎                   | 完全离线可用，回答来自内置规则 |

关键约束是：**任何一层坏掉，都不能让界面变成空白或者转圈不停。** 做菜这个场景里，模型回答得平庸不是事故，回答不出来才是。

## 阈值这件事必须调，默认值几乎一定是错的

意图路由用 dense embedding 加 BM25 的混合检索。默认相似度阈值是 1.0，实际跑起来真实问句的相似度在 0.69 附近——意味着几乎所有请求都掉进兜底分支，看起来「AI 完全不懂我在问什么」，而日志里一切正常。降到 0.55 之后才符合直觉。

这类问题的共性是：它不报错。功能存在、链路通、返回正常，只是答非所问。

## 降级带来的反面代价

静默降级的对偶是**静默故障难以发现**。小程序端的 WebSocket 客户端设了 8 秒连接超时、90 秒运行超时、30 秒心跳，连不上就悄悄换成本地规则回答。结果就是：链路整个坏掉时，界面上完全看不出来。

因此定了两条纪律：

- 验证真实连通性要看开发者工具的 socket 面板和后端日志，不看界面表现。
- 聊天地址必须是 `ws://` / `wss://` 前缀。写成 `http://` 不会报错，只会静默失败，然后一直走本地规则。这种错误连日志都没有，只能靠预先检查配置。

## 会话状态可插拔的另一个好处

检查点存储做成可替换之后，本地开发不必强依赖 Redis 就能跑完整链路，测试也能开出干净的实例。但这也带来一次坑：生产上用了不带 JSON 与 Search 模块的普通 Redis，检查点静默退化成内存，表现为「服务重启后所有会话上下文消失」，而健康检查全绿。依赖的**模块能力**也要写进部署清单，只确认镜像能启动是不够的。

## 一句话总结

把「坏掉」当成正常状态来设计，然后为这个设计付一笔排障成本的债，并用日志纪律去还。不还的话，你会在用户反馈「AI 变傻了」的时候毫无头绪。
