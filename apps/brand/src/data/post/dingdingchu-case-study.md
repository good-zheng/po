叮叮厨要解决的问题很小：跟着菜谱做菜时，人总是腾不出手。看一步、洗菜、切菜，回头忘了刚才读到哪。所以要语音把步骤读出来，要计时结束响一声，要在问「现在该干什么」的时候有人回答。

难点全在「有人回答」这五个字上。

## 端上先分成三种，但只允许有一份事实

小程序（Taro + React）是主入口，App（Expo + React Native）负责体验完整版，管理后台（Umi Max + Ant Design）负责内容维护。三个端各说各的字段名，是这类项目最贵的错误来源，所以从第一天起，跨端契约单独成为一个包，字段变更先改它，再看编译器在哪些地方报错。

响应协议也统一成一个信封：所有 HTTP 接口返回同一个包装结构，分页字段语义一致。这样任何一个端换后端框架都不用改解析逻辑，反之亦然。

## 后端拆成两个，不是因为洁癖

业务侧（菜谱、分类、用户、审批、文件、语音合成）交给 Spring Boot，理由很实在：这类 CRUD 与权限的组合在 Java 生态里最顺手，持久层用 MyBatis-Plus，表结构由 `schema.sql` 掌管，而不是让 ORM 偷偷建表——建表语句是唯一能被审的版本。

AI 侧交给 FastAPI。意图路由、Agent 编排、向量检索这些能力只有 Python 生态跟得上。它对外只暴露一个 WebSocket 端点，会话标识贯穿始终。

两边各自部署，同步接口互不调用，避免一条链路抖动拖垮另一条。

## 语音这件事比想象中重要

做菜时唯一能用的感官是听觉。所以步骤要能读出来，而且读出来要快要稳。做法是：后端把合成好的音频放进对象存储，接口只返回 URL；小程序进详情页或做菜页就批量预热，命中缓存直接播放，未命中在后台合成。这样真正开始做菜时，所有音频都已经在本地了。

计时结束敲一下铃，做完成播一句祝贺。这类细节不做，产品就还是「一个能读的网页」。

## 中途砍掉了一条业务线

这个项目最初还带着一条毫不相干的业务线。确认它不会真的去做之后整块删掉，包括它的页面、模型和文档。半途而废的功能比没有功能更贵：它会让每一次改动都要多问一句「这个还要不要」。

## 现在的样子

四个能跑的端、两个后端服务、一百九十多个自动化测试用例、四层降级路径。小程序已经是体验版，公开访问入口还卡在域名配置这一步——这也是这类项目真实的最后 5%：技术做完了，平台规则还没伺候好。
